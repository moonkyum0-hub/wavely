# 파도 점수(calcWaveScore) 재설계

## 배경

사용자가 "사용자들이 파도 점수가 뭔지, 어떻게 산출되는지 의문을 가질 것 같다"고 지적하며 시작된 논의.
현재 공식(`src/lib/models.ts`)은 수면 35% + 운동 30% + 수분 20% + 컨디션 15%, 목표치는 8h/30분/2000ml로
고정 하드코딩되어 있는데, 이 가중치와 목표치 모두 어떤 연구·표준에서 나온 게 아니라 임의로 정해진 값이다.

의료/건강 연구 분야의 실제 종합 지표(SF-36, PROMIS, Framingham Risk Score)는 통계적으로 검증된 근거가
있고, Whoop/Oura 같은 소비자 앱은 센서 기반 생체데이터를 쓰며 정확한 가중치를 공개하지 않는다(정밀한
숫자로 오인되지 않게 방향성 신호로만 취급). Wavely의 현재 공식은 이 중 어느 근거도 없이 "그럴듯한 숫자"를
보여주고 있어, 프로젝트의 데이터 정직성 원칙(`CLAUDE.md`)에 위배된다.

## 목적 재확인

`COMPETITIVE_ANALYSIS.md`(Part 2-A)에 따르면 파도 점수를 만든 원래 목적은 두 가지:
1. 업계 수렴 패턴(Whoop/Oura/Samsung)을 따라 "한눈에 보는 오늘의 상태" 숫자 하나를 제공
2. 그 숫자를 "낮은 날도 흐름의 일부"라는 서사로 감싸 실패 프레임을 피함

현재 구현(모두에게 동일한 고정 절대 기준)은 목적 2와 오히려 충돌한다 — 절대 기준 미달은 실패로 읽히기 쉽다.
이미 페르소나별로 다른 목표치가 Goals 시스템에 존재하는데 점수는 이를 무시하고 있었다.

## 새 공식

**파도 점수 = 그날 기록된 지표(수면/운동/수분)의, 각자 사용자 목표 대비 달성률(0~100%로 캡)의 단순 평균**

- **컨디션은 점수에서 제외**한다. 컨디션은 목표가 있는 지표가 아니라 그날의 주관적 자가 체크라 "달성률"로
  환산하는 것 자체가 억지스럽다. 이미 Dashboard 주간 차트에 컨디션이 별도 라인(`condition: r.condition * 20`)으로
  표시되므로 가시성 손실은 없다.
- 가중치는 수면/운동/수분 **동일 비중(각 1/3)**. "35/30/20/15%"처럼 근거 없는 숫자 대신 "세 지표를 동등하게
  본다"는 그 자체로 설명 가능한 규칙.
- 목표치는 고정 절대값이 아니라 **사용자의 활성 Goals(`goalService.getActiveGoals()`)에서 가져온 실제 목표값**을
  사용한다. 사용자가 직접 바꾸지 않았다면 온보딩에서 고른 페르소나 기본값(`goalTemplates.ts`)이 그대로 쓰인다.
- 그날 **기록되지 않은 지표는 평균에서 제외**한다(0%로 취급하지 않음 — 완벽주의 방지 원칙). 세 지표 모두
  기록이 없으면 점수는 `null`(빈 상태 "–").

### 예시
목표가 수면 8h/운동 30분/수분 2L이고 오늘 수면 6h·운동 45분·수분 1L을 기록했다면:
수면 6/8=75%, 운동 45/30→100%(캡), 수분 1/2=50% → 평균 (75+100+50)/3 = **75점**.

## 데이터 흐름 / 구현 구조

`calcWaveScore`는 순수 함수로 유지한다 (테스트 용이성, `CLAUDE.md` 테스트 정책). DB 조회(목표값 가져오기)는
함수 내부가 아니라 호출부의 책임으로 분리한다.

```ts
// src/lib/models.ts
calcWaveScore(
  record: Partial<HealthRecord>,
  targets: { sleep: number; exercise: number; water: number }
): number | null
```

- 호출부(`src/lib/healthService.ts`의 `upsertRecord`)가 저장 시점에 `goalService.getActiveGoals()`로
  현재 활성 목표를 조회한 뒤 `{ sleep, exercise, water }` 형태로 추출해 넘긴다. 목표가 없는 항목은
  `goalTemplates.ts`의 `DEFAULT_GOAL_TEMPLATE` 값으로 대체한다.
- 점수는 지금과 동일하게 **저장 시점에 계산되어 DB에 고정**된다. 이후 목표가 바뀌어도 과거 날짜의 저장된
  점수는 재계산되지 않는다 — 기존 동작과 동일한 원칙이라 별도 마이그레이션 스크립트 불필요.
- 기존에 DB에 저장된 과거 레코드(현재 2건: 2026-07-14, 2026-07-22)는 옛 공식으로 계산된 값을 그대로 둔다.
  재계산하지 않는다 — 데이터 양이 적어 실질적 영향이 미미하고, 과거 시점의 목표값을 정확히 복원할 방법이
  없기 때문.

## Goals 화면의 "파도 점수" 항목

`goalTemplates.ts`에 이미 존재하는 `type: "wave"` 목표(목표치 70~80점)는 **변경 없음**. 파도 점수가
"목표 대비 평균 달성률"이 되어도 "그 평균이 80% 이상이길 바란다"는 여전히 유효한 목표이며(Whoop의
"회복 점수 67% 이상" 같은 메타 목표와 동일한 성격), Goals 페이지의 표시/진행률 바 로직도 그대로 작동한다.
