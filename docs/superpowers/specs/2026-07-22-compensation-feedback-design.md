# 상호보완 피드백 (Compensation Feedback) 설계

> **For agentic workers:** 다음 단계는 superpowers:writing-plans로 이 스펙을 구현 계획으로 변환하는 것.

## 배경 & 동기

사용자는 모든 축(수면·운동·수분·컨디션)에서 매일 완벽할 수 없다. 한 축이 부족하면
다른 축으로 채우거나, 강도를 낮춰서 회복에 집중하는 게 몸의 항상성 기전과 비슷하다는
컨셉이다. 목적은 두 가지:

1. 완벽하지 않아도 몸의 다른 부분이 커버할 수 있다는 걸 보여주기 (완벽주의 방지 원칙과 직결)
2. 사용자가 지치지 않게 하기 — 하나 놓쳤다고 전체를 포기하지 않도록

## 범위 (v1)

**다루는 축**: 수면 / 운동 / 수분 (`Goal.type`에 이미 존재하는 세 축) + 컨디션(별도 처리, 아래 참고).

**제외**:
- `wave`(파도 점수) 목표 — 세 축의 가중합 결과물이라 별도로 걸면 같은 원인을 중복 안내하게 됨
- 인지검사 축 — 이번 범위 밖 (추후 로드맵에서 재검토)
- 목표 없는 사용자 대응 — 목표가 없는 축은 판정 자체를 건너뜀 (에러 아님)

## 아키텍처

**새 파일**: `src/lib/compensation.ts` — 정적 규칙 데이터 + 순수 판정 함수를 한 파일에 둔다.
`bodyFunctions.ts`와 같은 결(데이터+로직 한 파일, `*Service.ts`가 아님 — DB를 직접 안 건드리는
순수 함수라서). 테스트는 `compensation.test.ts`.

**타입**:

```ts
export type CompensationResult =
  | { mode: "recovery"; message: string }
  | { mode: "compensation"; deficientAxis: "sleep" | "exercise" | "water"; message: string };
```

**함수 시그니처**:

```ts
export function computeCompensation(
  records: HealthRecord[],
  goals: Goal[]
): CompensationResult | null;
```

- `records`: 최근 3일치. Dashboard가 이미 `getRecentRecords(21)`로 가져오는 배열을 그대로 넘김
  (추가 DB 호출 없음, 함수 내부에서 최근 3일만 골라 씀).
- `goals`: `getActiveGoals()` 결과. Dashboard가 현재 호출하지 않고 있어 새로 추가해야 함.

## 판정 로직

**"최근 3일"의 정의**: 오늘을 포함한 달력 기준 3일(오늘·어제·그저께). 이 3일 중 기록이 있는
날짜만 평균에 넣는다 (예: 오늘·그저께만 기록 있으면 2일치 평균, 어제 기록 없다고 0으로 안 침).
`records` 배열(최근 21일치)에서 이 3개 날짜에 해당하는 항목만 걸러서 쓴다.

1. **컨디션(회복 모드) 먼저 체크.** 최근 3일 중 기록 있는 날의 컨디션 평균이 **2점 이하(5점 만점)**면
   `{ mode: "recovery", message: ... }`를 즉시 반환하고 아래 단계는 건너뜀. 컨디션은 회복 모드
   임계값 하나만 둔다 — 다단계 세분화는 지금 단계에서 과설계라 v1 범위 밖으로 미룬다.
2. 회복 모드가 아니면 수면/운동/수분 각각에 대해 "최근 3일 중 기록 있는 날의 평균 vs 해당 축의
   활성 목표(`targetValue`)"를 비교. 목표가 없는 축은 판정에서 제외.
3. 미달 축이 하나 이상이면, **목표 대비 부족 비율**(`(target - actual) / target`)이 가장 큰 축
   하나를 골라 규칙 테이블에서 메시지를 찾아 `{ mode: "compensation", deficientAxis, message }` 반환.
4. 미달 축이 없거나, 최근 3일 중 기록이 하루도 없으면 `null` 반환 — 이땐 UI가 아무것도 안 보여줌
   (데이터 정직성 원칙 — 근거 없이 긍정 메시지도 지어내지 않음).

**미기록일 처리**: 평균은 항상 "기록이 있는 날"만으로 계산한다. 기록 없는 날을 0으로 치지 않는다
(이미 Dashboard 다른 곳에서 쓰는 패턴과 동일 — 기록 없음을 벌점으로 안 씀).

## 규칙 테이블 (보완 제안)

| 부족 축 | 메시지 |
|---|---|
| 수면 | "요즘 잠이 부족했어요. 오늘은 운동 강도를 살짝 낮추고, 평소보다 30분 일찍 잠자리에 들어보는 건 어때요?" |
| 운동 | "요즘 몸을 많이 못 움직였어요. 오늘은 가벼운 스트레칭이라도 5분만 추가해보는 건 어때요?" |
| 수분 | "요즘 물을 충분히 못 마셨어요. 물 한 컵을 눈에 보이는 곳에 두고 마셔보는 건 어때요?" |

## 회복 모드 메시지

컨디션 3일 평균 ≤ 2일 때 (다른 축 결과 무시):

> "요즘 컨디션이 낮았어요. 오늘은 목표를 다 채우려 하지 말고 회복에 집중하는 날로 삼아보세요 —
> 파도는 다시 올라와요."

## 카피 가드레일

`bodyFunctions.test.ts`와 동일한 정규식으로 위 4개 메시지를 자동 검사한다:

```ts
/향상시|훈련하|좋아집니다|개선됩니다/
```

새로 추가하는 메시지는 전부 이 정규식을 통과해야 하며, `compensation.test.ts`에 동일 가드레일
테스트를 둔다 (효능 단정 없이 관찰·제안 언어만 사용).

## UI

**배치**: Dashboard의 "7일 파도 흐름" 카드와 "오늘의 파도 구성 / 연속 기록" 그리드 사이에 새 카드.

**렌더 조건**: `computeCompensation`이 `null`이면 컴포넌트가 아예 렌더링되지 않음 (EmptyState도
안 씀 — 조용히 안 보이는 편).

**스타일**: 기존 트렌드 인사이트 줄(아이콘 + 왼쪽 컬러 보더 + 텍스트)과 같은 톤을 재사용하되,
**"Gemini AI" 배지는 붙이지 않는다** — 이 기능은 규칙 기반 로직이지 AI가 아니므로, 배지를 붙이면
사용자에게 잘못된 인상을 준다. 모드별 아이콘:
- 회복 모드: `Leaf` (lucide-react) — 기존 Moon/Flame/Droplets와 겹치지 않는 차분한 톤
- 보완 제안: 해당 축 아이콘 재사용 (수면=Moon, 운동=Flame, 수분=Droplets — 이미 Dashboard.tsx에 import됨)

## 에러 처리

`getActiveGoals()` 호출을 Dashboard의 기존 데이터 로딩 `useEffect`/`try-catch` 안에 포함시킨다
(CLAUDE.md의 "dev browser mode" 패턴). Tauri DB가 없는 브라우저 미리보기에서는 `goals`가 빈
배열이 되고, `computeCompensation`은 목표 없는 축을 건너뛰므로 자연히 `null`을 반환해 카드가
안 보인다. 별도 에러 UI 없음.

## 테스트 계획 (`compensation.test.ts`)

- 축별 3일 평균 vs 목표 판정이 정확한지
- 기록 없는 날은 평균 계산에서 제외되는지
- 최근 3일 중 기록이 하루도 없으면 `null`인지
- 컨디션 낮음 + 다른 축도 부족 → 회복 모드가 항상 우선하는지
- 여러 축이 동시에 미달일 때 부족 비율이 가장 큰 축 하나만 선택되는지
- 4개 메시지 전부 카피 가드레일 정규식을 통과하는지

컴포넌트/통합 테스트는 만들지 않는다 (기존 CLAUDE.md 테스트 정책과 동일 — Dashboard 통합 부분은
브라우저에서 직접 목업 데이터로 확인하는 수동 검증으로 대체).

## 범위 밖 (v1에서 하지 않음)

- 인지검사 결과를 축에 포함
- 컨디션 회복 모드의 다단계 임계값 (예: 1점대는 더 강한 메시지)
- 사용자가 판정 기간(3일)을 직접 설정
- 커스텀 목표 타입(`custom`)에 대한 보완 규칙
